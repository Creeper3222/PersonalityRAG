# Operational baseline (2026-07-10)

Baseline commit: `721b47f01087f56489624b21782619f80df104fe`.

The measurements below were collected from the Windows live process with five
sequential warm requests per endpoint. They are diagnostic baselines, not
performance assertions; machine load and database size affect them.

| Endpoint/resource | Mean | Observed p95 | Bytes |
| --- | ---: | ---: | ---: |
| `GET /api/v1/health` | 16.03 ms | 35.87 ms | 120 |
| `GET /api/v1/libraries` | 87.21 ms | 107.96 ms | 13,503 |
| `GET /api/v1/stats` | 91.68 ms | 131.81 ms | 5,447 |
| `GET /static/app.js` | 116.74 ms | 121.81 ms | 244,966 |

Static `app.js` was returned with `Cache-Control: no-store, max-age=0`, no
`Content-Encoding`, and an ETag. The live process reported 88 threads, 87.43
MiB working set, and 4,874.24 MiB private bytes at the sample point.

The Python 3.11 baseline suite completed 112 tests in 13.79 seconds. One
`aiosqlite` worker warning showed a connection finishing after its test event
loop had closed; resource ownership is tracked as an operational regression
target.

## Query and provider-call baseline

- `ControlStore.list_libraries()` performs one list query and then calls
  `get_library()` once per row.
- `LibraryManager.list_libraries()` also resolves provider revisions per
  library and computes full storage statistics per loaded library.
- `GET /stats` invokes the bound provider connection test on each request.
- `JobManager.wait()` polls SQLite every 50 ms until a terminal state.

These call patterns are intentionally documented before Batches 3 and 5. The
optimized implementations must preserve response contracts while reducing
polling, repeated database reads, and repeated provider probes.
